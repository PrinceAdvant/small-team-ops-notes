Writing an incident runbook for a single-server app

A runbook is the page you open when the site is down and your heart rate is up. For a single-server app it does not need to be long. It needs to be in the right order and written before the incident.

Put it where you can reach it during an outage

Not on the server that is down. A Git repo, a shared doc or a printed page all work.

Section 1: confirm the problem

  • Check the site from outside your network, for example with a phone on mobile data
  • Check your uptime monitor for when it started
  • Note the time; you will need it for logs

Section 2: is the server alive?

ssh deploy@server
uptime
df -h
free -m

Disk full and memory exhaustion cause a large share of single-server outages. If SSH itself fails, go to the provider console and check whether the machine is running.

Section 3: are the containers running?

docker ps -a --format '{{.Names}}  {{.Status}}'

Look for containers that are restarting or exited. Then read logs for the window you noted:

docker logs --since 30m app

This is where good logging pays off. If logs are huge and unstructured, finding the first error takes much longer.

Section 4: common fixes, in order of risk

  1. Restart the failing container
  2. Free disk space by pruning old images and build cache
  3. Roll back to the previous image or release
  4. Restart the Docker daemon
  5. Reboot the server

Write the exact commands for your setup next to each step.

Section 5: communicate

Post a short status note even if you do not know the cause yet. "We are aware the site is down and investigating" buys patience.

Section 6: after recovery

  • Record the timeline while you remember it
  • Capture logs before they rotate away
  • Write one or two follow-up actions, not twenty

Keep it current

Every time you use the runbook, fix whatever was wrong or missing. Review it when you change hosting, proxy or database setups. A stale runbook with old container names is almost as bad as none.

Practice once

Pick a quiet afternoon, stop a non-critical container on staging and follow the runbook as if it were real. You will find at least one missing command or outdated path.

Good logs make every section above faster. This guide on Docker logging practices explains rotation, structure and retention.
