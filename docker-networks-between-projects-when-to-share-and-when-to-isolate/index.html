Small Team Ops Notes

Docker networks between projects: when to share and when to isolate

When several projects run on one server, Docker networking decides which containers can talk to each other. The default Compose behavior, one network per project, is a good start. Problems appear when projects need to share something, such as a reverse proxy or a database.

The default: one network per project

Compose creates a network named after the project. Services inside it reach each other by name. Containers from other projects cannot reach them unless you connect the networks. This isolation is valuable: a compromised app in one project cannot scan the database of another.

The reverse proxy exception

A single reverse proxy usually fronts all projects. The common pattern is an external network, for example proxy, created once:

docker network create proxy

Each app joins both its own project network and proxy. The database joins only the project network. The proxy can reach the app; it cannot reach the database.

Sharing a database between projects

Avoid it when you can. If two apps truly need the same database, prefer:

  1. A dedicated network containing only the database and the apps that need it
  2. Separate database users with access to separate schemas

Do not put every container on one big shared network for convenience. It removes the isolation that made Compose networks useful.

Internal networks

Mark networks that should never reach the internet as internal:

networks:
  backend:
    internal: true

Containers on an internal network cannot make outbound connections, which is a useful guard for databases.

Published ports bypass all of this

ports: - "5432:5432" exposes the database on the host, outside the network model, and often to the internet. Only publish ports for the reverse proxy. Use 127.0.0.1:5432:5432 if you need local access for maintenance.

DNS names

Within a network, use service names, not container IPs. IPs change when containers are recreated. If two projects on a shared network use the same service name, such as db, add network aliases to avoid confusion.

Quick audit

Run docker network ls, then docker network inspect on each network and list the containers attached. Any database attached to the proxy network, or any unexpected published port, is worth fixing.

For the basics of bridge networks, DNS and port publishing, this guide to Docker networking is a good reference.
